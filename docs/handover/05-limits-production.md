# Ограничения и что нужно для production

## Что в прототипе не проверено

| Что | Почему |
|---|---|
| **Новый путь LLM функции 1 в живом режиме** | существующая Qwen старого помощника на Bult проверена 13 октября, но это другой путь вызова; есть ошибка рекомендации — см. [07](07-bult-live-verification.md). Для нового пути реальные ключи и вызовы не использовались. Реальные провайдеры (`openai`, `anthropic`) проверены против подставного HTTP-сервера (запрос, ответ, ошибки 401/403/429/5xx, таймаут, обрыв, редирект). Живой запрос через новый путь функции 1 не выполнялся, поэтому его расходы в [06-llm-cost.md](06-llm-cost.md) — оценка по числу токенов, а не измерение |
| **Интеграция с реальным Bult MCP/API** | по ТЗ принимается отдельно. Прототип работает с реестром образов, npm и GitHub напрямую |
| **Нагрузка и параллельная работа нескольких пользователей** | проверялась только корректность (изоляция по владельцу, отсутствие дубликатов), производительность не измерялась |
| **Исправление в работающем приложении** | система проверяет опубликованный образ. Какой образ запущен в эксплуатации, она не наблюдает и так и пишет в отчёте |

## Ограничения первой версии (как в ТЗ и по реализации)

| Ограничение | Что это значит |
|---|---|
| Один стек: Node.js и npm | остальные экосистемы (pip, Maven и т.д.) агент исправлений не обновляет; находки по ним остаются на ручном разборе |
| Только обновление зависимостей | в агенте функции 1 изменения кода, конфигурации и Dockerfile не готовятся |
| Пакеты ОС и инструменты базового образа не исправляются автоматически | в новом запуске агента 256 находок относятся к ОС/инструментам образа; отдельно ручного решения требуют пакеты приложения. 259 из 263 — прежнее общее число MANUAL_REVIEW в историческом отчёте, а не число находок ОС |
| Если исправленной версии нет или обновление меняет мажорную версию | ручное рассмотрение; обновление, которое ломает сборку, тесты или запуск, в PR не попадает |
| Образы только из реестров из списка `IMAGE_ALLOWED_REGISTRIES`, без авторизации в реестре | приватные реестры не поддерживаются |
| Исходники только из публичных репозиториев GitHub | приватные репозитории не поддерживаются |
| Песочница использует Docker на той же машине | сборка идёт с сетью, поэтому проект должен быть доверенным (учебным). Образ приложения должен содержать Node.js (`/health` проверяется командой `node` внутри контейнера) |
| База уязвимостей Trivy не старше 48 часов (`IMAGE_DB_MAX_AGE_HOURS`) | более старая база останавливает проверку с ошибкой, а не даёт «чистый» результат. Кэш базы около 1,4 ГБ |
| Агент исправлений, PR и подтверждение применения запускаются скриптами | HTTP-интерфейса для них нет: человек подтверждает действие в терминале (для PR нужно ввести имя репозитория) |
| Нет веб-интерфейса для проверок образов, отчёта и исправлений | работа через API и скрипты. Существующий интерфейс платформы эти разделы не показывает |
| Один worker, задания выполняются по очереди, не больше 10 заданий в очереди | достаточно для демонстрации, не для нагрузки |
| Сканирование не блокирует деплой | так задано в ТЗ; скрипт CI возвращает код 0, кроме режима `--strict` для ошибки запуска проверки |

## Что нужно для production

| Область | Что нужно |
|---|---|
| Интеграция с Bult | события «образ собран / опубликован» из Bult вместо ручного запуска из CI; список образов, запущенных в эксплуатации (по нему «исправление применено» станет «исправление работает в эксплуатации»); приёмка на выделенном стенде |
| Авторизация CI | в прототипе один токен действует от имени одного владельца и разрешает только запуск и чтение проверок. Для production нужны токены на проект с выпуском, отзывом, ротацией и записью в журнал |
| Секреты | ключ модели и токен записи в GitHub должны храниться в хранилище секретов платформы. Токен записи для PR лучше заменить GitHub App с минимальными правами |
| Песочница | отдельный изолированный исполнитель (не Docker Desktop на ноутбуке) с ограничением ресурсов и сети; ответ на вопрос, где его запускать на Bult |
| Языковая модель | выбрать провайдера и модель, задать бюджет и цены в `LLM_PRICE_*`, решить политику данных (наружу уходят название пакета, версии, CVE и заголовки находок), включить мониторинг расходов и хранение `llm_calls` ограниченное время |
| Приватные источники | доступ к приватным реестрам образов и репозиториям |
| Эксплуатация | мониторинг и оповещения о сбоях сканера и устаревшей базе; несколько worker; очистка старых проверок и запросов к модели; резервное копирование базы |
| Другие стеки | при необходимости расширить агент исправлений на pip, Maven и т.д. |

## Вопросы к ментору

1. Какого провайдера и модель использовать и какой бюджет на расходы? От этого зависят цены в настройках и итоговая оценка расходов.
2. Можно ли отправлять во внешнюю модель названия пакетов, версии, CVE и заголовки находок? Код, пути, секреты и адреса репозиториев не отправляются.
3. Какой способ авторизации CI на production-сервере предпочтителен? Прототип использует токен с ограниченными правами.
4. Где на Bult запускать песочницу, которой нужен Docker?
5. Откуда брать образы: нужны ли приватные реестры?
6. Нужны ли приватные репозитории GitHub?
7. Как часто перепроверять опубликованные образы (в прототипе раз в 24 часа) и какой предельный возраст базы уязвимостей считать допустимым (в прототипе 48 часов)?
8. Нужен ли веб-интерфейс для отчёта и исправлений, или достаточно API и скриптов?
9. Достаточно ли того, что модель пишет описание изменения для PR, а версии и файлы определяет код? Если нужно, чтобы модель предлагала сами изменения файлов, нужны дополнительные проверки, потому что текст модели не должен исполняться напрямую.

## Подтверждённые ограничения и неисправности окружения

- В двух исходных проверках `3bd56c8b` и `4247ede4` Trivy завершился успешно, но Gitleaks и Semgrep не установлены. Это прямо записано в `scanner_results` и подтверждено поиском исполняемых файлов в окружении worker. Статус `FAILED`, итог отчёта `INCOMPLETE`; успешные находки Trivy сохранены.
- Проверка `e7065736` завершилась `CHECKOUT_FAILED`: код зафиксировал невозможность загрузить репозиторий. Точная первопричина старого сетевого/ Git-сбоя не сохранена; утверждать, что это были отсутствующие сканеры, нельзя. Более поздние проверки успешно загрузили исходники.
- Сборка и запуск из вложенных тестовых данных сначала не удались из-за прав 0600/0700. Права исправлены на 0644/0755, повторный запуск завершился `STILL_DETECTED`. Оба результата сохранены.
- Тест настроек зависел от внешней переменной `LLM_PROVIDER`; тест теперь очищает её перед проверкой значения по умолчанию. Лог первой неудачи сохранён.
- Исправлена потеря метки коммита при сохранении результата сканирования образа. Коммит из корректной `org.opencontainers.image.revision` теперь виден в отчёте и находках. Без метки он остаётся неизвестным; старые записи задним числом не менялись.
- Метка коммита — заявление сборщика. Она не является криптографическим доказательством того, какие исходники использовались. Для production нужны доверенная сборка и подтверждение происхождения образа.
- Песочница не запускает тесты исходной версии до обновления. Поэтому `BREAKS_APP` означает ошибку после изменения, а универсальная причинная связь не доказана. Конкретный сценарий uuid подтверждён сообщением несовместимости загрузки `uuid/v4`.
- Сравнение с историческим отчётом может показать новые уязвимости из-за изменения базы CVE или исходного состава зависимостей. Общее число находок не доказывает эффект патча. Сценарий lodash явно описывает это ограничение.

## Открытые пункты ТЗ

Эти пункты нельзя объявить выполненными на 100% по локальным fake-вызовам:

1. Живой запрос через новый путь пояснений функции 1 и измеренный расход. Старый помощник с Qwen на Bult проверен, но это не подтверждает новый путь. Подробности и обнаруженная ошибка ответа — в [07](07-bult-live-verification.md).
2. Тестовый адаптер ресурсов Bult и подключение выделенного стенда через Bult MCP/API. В коде есть адаптеры LLM; это **не** адаптеры Bult. Доступ к существующему стенду через Safari проверен, но программный адаптер не реализован и Bult MCP/токен в текущем окружении не настроены. ТЗ допускает отдельную приёмку интеграции.
3. Привязка подтверждённого опубликованного образа к действительно работающему сервису Bult. Сейчас это не наблюдается.
4. Повторное создание/слияние PR и подтверждение через настоящий GitHub в этой сдаче не запускались из-за прямого запрета владельца. Исторический `CONFIRMED` прочитан из базы, а не перепроверен на GitHub.
