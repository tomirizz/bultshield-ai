# Архитектура и API

Живой статус на 14 октября и точная граница облачной интеграции — [08](08-function1-live-acceptance.md). Новый `bult_llm.py` подключает существующий приватный llama.cpp, `ImageChecks.tsx` показывает проверки/отчёты в проекте. `GET /api/checks-configuration` возвращает только безопасные настройки, доступные владельцу: реестры, период, имя провайдера и отсутствие облачной песочницы. Песочница и операции PR ниже относятся к отдельным скриптам, не к работающему веб-циклу Bult. Выбор версий обновления языковой моделью (любой провайдер) описан в [10](10-llm-planner.md).

## Схема

```
 Разработчик / CI                      ┌──────────────────────────────────────────────┐
   │  POST /api/checks                 │ PostgreSQL                                   │
   ▼                                   │  scans, scan_jobs (очередь), findings,       │
 ┌──────────┐   ставит задание ───────▶│  dependency_fix_runs, llm_calls, llm_jobs    │
 │   API    │◀── читает результат ─────│                                              │
 │ FastAPI  │                          └───────────────▲──────────────────────────────┘
 └──────────┘                                          │ берёт задания, пишет результат
                                           ┌───────────┴───────────┐
                                           │        Worker         │
                                           │ • проверка образа     │──▶ реестр образов (только чтение)
                                           │   (Trivy)             │──▶ база уязвимостей Trivy
                                           │ • перепроверки по     │
                                           │   расписанию          │
                                           │ • пояснения модели    │──▶ LLM API (ключ только на сервере)
                                           └───────────────────────┘

 Скрипты (по подтверждению человека):  агент исправлений ──▶ план версий (реестр npm)
                                                          ──▶ песочница Docker (установка, тесты, сборка, запуск, повторный скан)
                                                          ──▶ выбор версии (модель, из набора, заданного кодом)
                                                          ──▶ описание изменения (модель) ──▶ PR на GitHub
                                       подтверждение применения: PR слит + образ пересобран + повторный скан
```

## Жизненный цикл находки (статусы ТЗ)

```
 Проблема обнаружена ─▶ Исправление предложено ─▶ Исправление прошло проверку ─▶ Исправление применено к приложению
        │                                                 │
        └──────────────▶ Требуется ручное вмешательство ◀─┘   (нет исправленной версии, обновление ломает приложение,
                                                               находка осталась, результат нельзя определить)
```

| Статус (код) | Когда ставится | Кто и что подтвердил |
|---|---|---|
| Проблема обнаружена (`FOUND`) | Trivy нашёл уязвимость в образе | сканер, для конкретного digest образа |
| Исправление предложено (`FIX_PROPOSED`) | выбрана версия для обновления | код по данным реестра npm; ничего не проверено |
| Идёт проверка исправления (`VERIFYING`) | песочница работает | служебное состояние |
| Исправление прошло проверку (`FIX_VERIFIED`) | в песочнице прошли установка, тесты, сборка, запуск, `/health`, повторный скан: целевые находки исчезли, новых нет | песочница, на копии проекта |
| Исправление подтверждено в опубликованном образе (`FIX_DEPLOYED`) | PR слит (проверяет GitHub), образ собран после слияния, повторный скан нового образа не видит находку, а пакет в нём виден | доказательства из GitHub и повторного скана; относится к **опубликованному образу** |
| Требуется ручное вмешательство (`MANUAL_REVIEW`) | нет исправленной версии; обновление ломает сборку/тесты/запуск; находка осталась; обновление меняет мажорную версию; пакет ОС или инструмент базового образа; проверка не завершилась | причина записана в `status_reason` |

## Что делает каждая часть

| Часть | Файлы | Ответственность |
|---|---|---|
| Сканирование образа | `image_scan.py`, `image_report.py`, `image_pipeline.py` | скачать образ из разрешённого реестра, прогнать Trivy, разобрать отчёт, записать находки с привязкой к digest. Образ только читается, не запускается |
| Единый формат находки | `image_pipeline.py`, модель `Finding` | проблема (`title`, `rule_id`, `cve`), критичность (`severity`), компонент (`package`, `installed_version`), источник (`scanner`, `origin`: приложение / ОС / инструменты образа), возможное исправление (`fixed_version`, `manual_reason`) |
| Отчёт | `check_report.py` | факты, предположения и предложенные действия **раздельно**; вердикт; сравнение с прошлой проверкой; ограничения |
| Агент исправлений | `fix_agent.py`, `dependency_fix.py`, `npm_registry.py` | выбрать версию для каждого пакета, проверить в песочнице по одному и затем набором, присвоить статус |
| Песочница | `sandbox.py` | изолированная копия проекта в Docker: `npm install` без запуска скриптов, тесты без сети, сборка образа, запуск без сети и проверка `/health`, повторный скан |
| PR | `github_pr.py` | ветка, один коммит с `package.json` и `package-lock.json`, PR. Только после подтверждения человеком и только в репозитории из списка разрешённых |
| Подтверждение применения | `fix_deployment.py` | проверить доказательства (слит ли PR, новый ли образ, видна ли находка в повторном скане) |
| Пояснения модели | `llm.py`, `llm_explain.py`, `llm_jobs.py`, `llm_report.py` | запросы к модели, проверка ответа, лимиты, учёт токенов и расходов, фоновое задание |
| Выбор версии моделью | `llm_plan.py`, `dependency_fix.candidate_versions`, `fix_agent.py` | код задаёт набор допустимых версий, модель выбирает одну и объясняет выбор, песочница проверяет, при отказе действует версия правил. Подробно — [10](10-llm-planner.md) |
| Описание изменения для PR | `llm_change.py` | текст «что меняется / что может сломаться / на что посмотреть» к уже проверенному набору обновлений |
| Запуск после сборки | `scripts/ci_check.py`, `ci_token.py` | поставить проверку из CI, не блокируя деплой; токен CI даёт доступ только к запуску и чтению проверок |
| Перепроверка опубликованных образов | `image_rescan.py`, `image_history.py` | раз в `IMAGE_RESCAN_HOURS` часов перепроверить образы с пометкой «следить» и показать, что изменилось с прошлой проверки |

## API (функция 1)

Пути проверок начинаются с `/api`; пути здоровья `/health/live` и `/health/ready` находятся в корне. Ответы на русском, ошибки без внутренних деталей (без SQL, путей и секретов).

| Метод и путь | Что делает | Ответ |
|---|---|---|
| `POST /checks` | поставить проверку. Поля: `repository_id`; `image` **или** `commit`; `watch` (следить за образом); `trigger` (`api` или `ci`) | 202, проверка в очереди. Повтор того же образа возвращает уже идущую проверку, дубль не создаётся. 422 при неверном вводе, 429 при полной очереди |
| `GET /checks/{id}` | состояние проверки (`QUEUED` … `COMPLETED` / `FAILED`) | 200 или 404 |
| `GET /checks/{id}/report` | полный отчёт (структура ниже) | 200 |
| `POST /checks/{id}/explanations` | запросить пояснения модели в фоне | 202; 409, если модель не подключена или проверка не завершена; повтор возвращает то же задание |
| `GET /checks/{id}/explanations` | состояние задания пояснений и сводка по запросам к модели | 200 |
| `GET /scans`, `GET /findings` | история проверок и список находок (фильтры `scan_id`, `severity`, `scanner`) | 200 |
| `POST /projects` | создать проект с репозиторием | 201 |
| `GET /health/live`, `GET /health/ready` | жив ли процесс; доступна ли база и применены ли миграции | 200 / 503 |

Агент исправлений, создание PR и подтверждение применения запускаются **скриптами** (`scripts/run_fix_check.py`, `confirm_fix_deployment.py`): так человек подтверждает каждое действие. HTTP-интерфейса для них нет (см. ограничения).

### Структура отчёта

| Раздел | Содержимое |
|---|---|
| `check`, `subject` | какая проверка, её статус, коммит, образ, digest, что запустило проверку (`api`, `ci`, `schedule`) |
| `verdict` | итог одним предложением: `FINDINGS` (находки есть), `NO_FINDINGS` (только если все сканеры отработали; с оговоркой, что это не гарантия), `INCOMPLETE` (проверка выполнена не полностью: сбой сканера, нет результатов), `IN_PROGRESS`. **Сбой никогда не `NO_FINDINGS`** |
| `facts` | то, что измерили сканеры: версии сканеров, возраст базы, число находок по критичности, происхождению и статусам |
| `findings.items` | находки в едином формате с `status`, `status_text`, `status_reason`, `fix` |
| `changes_since_previous` | что нового и что исправлено по сравнению с прошлой проверкой того же образа; тот ли образ (по digest) |
| `fix_run`, `deployment` | результат агента исправлений и доказательства применения |
| `assumptions` | **предположения**: пояснения модели, помеченные именем модели |
| `proposed_actions` | **предложенные действия**: что делать человеку |
| `llm` | состояние модели: сколько пояснено, причины сбоев, токены, расходы, состояние фонового задания |
| `limitations` | что отчёт не гарантирует |

## Безопасность

| Требование ТЗ | Как выполнено |
|---|---|
| Ключи на backend | ключ модели читается из окружения сервера как скрытая строка; не попадает в ответы API, логи и сообщения об ошибках |
| В модель не уходят секреты, дампы БД, необработанные данные | модели передаются только название пакета, версии, идентификаторы и заголовки находок, статус. Перед отправкой текст проходит удаление секретов; код, пути, логи и адреса репозиториев не отправляются |
| Лимиты запросов, токенов, расходов | запросов на проверку, запросов в сутки, токенов ответа, таймаут; каждый запрос записан в `llm_calls` с токенами и расходами |
| Таймаут, ограничения API, некорректные ответы | недоступность, ошибка 401/403/429/5xx, обрыв сети различаются; после недоступности повторные запросы в этой проверке не отправляются |
| Проверка формата ответа; текст модели не исполняется | ответ должен быть JSON из трёх строк нужной длины (для выбора версии — четыре поля, версия только из набора кода), на русском, без ссылок, кода и секретов; версии и CVE только из переданных данных. Ничего из ответа не выполняется и не попадает в файлы изменения |
| Долгие операции в фоне | проверки, перепроверки и пояснения идут через очередь в БД; статус и результат сохраняются |
| Повтор не создаёт дубликатов | активная проверка того же образа возвращается, а не создаётся заново; на проверку не больше одного активного задания пояснений; PR для того же набора не создаётся дважды |
| Доступ пользователя | все запросы фильтруются по владельцу проекта; токен CI действует от имени одного владельца и только на запуск и чтение проверок |
| Адаптеры языковой модели | `fake`, `bult`, `openai` (включая совместимые серверы) и `anthropic` реализуют один интерфейс; можно подключить любого провайдера. Живая проверка — только приватная Qwen Bult; `openai`/`anthropic` проверены подставным HTTP-сервером, на своём ключе — скриптом `scripts/verify_llm_planner.py` |
| Тестовый адаптер Bult и реальные API Bult | В этой версии отсутствуют; это отдельный открытый пункт интеграции, а не свойство адаптеров LLM |
| Измеренное, предположение, действие раздельно | разделы `facts`, `assumptions`, `proposed_actions` отчёта |

## Границы доказательств

Скан образа связан с digest, проверка исходников — с SHA коммита, запуск исправления хранит оба значения. У исторических проверок образов `subject.commit_sha=null`; нельзя утверждать, что для каждого образа доказано соответствие коммиту. После исправления метка `org.opencontainers.image.revision`, если есть в образе, переносится также в `subject.commit_sha` и метаданные находок. Это проверено на реально собранном и просканированном локальном образе (`examples/revision-linked-report.json`). Доказательство происхождения сборки и связь с фактически работающим сервисом Bult не реализованы.

Существующий `FIX_DEPLOYED` означает подтверждение опубликованного образа по сохранённым данным GitHub и сканера; у `fix_run.applied_to_running_app` остаётся `false`.
