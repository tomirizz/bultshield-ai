# Расходы на LLM в демонстрационном сценарии

LLM — языковая модель для пояснений. **В описанном ниже локальном сценарии новая функция 1 использовала fake.** Использован `LLM_PROVIDER=fake`, модель `fake-explainer-1`, без API-ключа и внешних запросов. Числа ниже взяты из `evidence/llm-estimate.txt`, `llm-explanations.txt` и `llm-reuse.json`.

## Предварительный расчёт

Проверка `ef3146d5-d8c5-4474-adc2-49dd8041293e` содержит 52 группы находок по пакетам/версиям. Dry-run — расчёт без отправки запроса — запланировал 20 групп; 32 группы пропущены из-за лимита.

| Показатель | Результат |
|---|---:|
| Запланированные запросы | 20 |
| Приблизительные входные токены | 15 305 |
| Верхняя граница токенов ответа по настройке | 12 000 = 20 × 600 |
| Fake-вызовы в рабочем демо | 20 |
| Учёт fake: вход / выход | 15 305 / 2 453 |
| Повтор: переиспользованные результаты | 20 |
| Повтор: новые входные / выходные токены | 0 / 0 |

Токен — единица текста, которую считает модель. Оценщик проекта использует `ceil(число символов / 3)`, отдельно для каждого запроса с системной инструкцией. Это грубая оценка, не токенизатор выбранной модели. Числа `fake` тоже синтетические, а не измеренный расход настоящего провайдера. Dry-run показывает стоимость полного выбранного набора без учёта уже готового кэша; повторный настоящий запрос может стоить меньше благодаря переиспользованию.

## Формула

Пусть `P_in = LLM_PRICE_INPUT_PER_MTOK`, `P_out = LLM_PRICE_OUTPUT_PER_MTOK` — цена за миллион входных/выходных токенов в долларах у выбранного провайдера.

`C = (T_in × P_in + T_out × P_out) / 1 000 000`.

Для этого dry-run: `C_estimate = (15 305 × P_in + 12 000 × P_out) / 1 000 000`.

12 000 — верхний предел ответа; вход оценён приблизительно, поэтому это не гарантированный денежный потолок. Тарифы здесь не выдумываются: их нужно взять у согласованного с ментором провайдера. Настройки цены сейчас нулевые; напечатанные `$0.0000` означают расчёт с незаданными ценами и не подтверждают бесплатность реальной модели.

## Ограничения и повторное использование

- `LLM_MAX_CALLS_PER_CHECK=20`: берутся первые 20 групп, остальные явно отмечаются как непояснённые. В выполненном демо результат пояснений `PARTIAL`, а задание завершено `COMPLETED`.
- `LLM_DAILY_CALL_LIMIT=200`: учитываются отправленные вызовы за последние 24 часа; при достижении лимита новые запросы прекращаются. Это скользящее окно, не сброс в полночь.
- `LLM_MAX_OUTPUT_TOKENS=600`: максимальная длина одного ответа.
- `LLM_TIMEOUT_SECONDS=30`: ограничение ожидания ответа.
- `input_hash`: отпечаток версии инструкции, провайдера, имени модели и подготовленных данных. Успешный результат с тем же отпечатком для той же проверки переиспользуется; новые данные или другая модель требуют нового вызова. Сбой не равен успешно закэшированному ответу.

Живое подтверждение повтора — `evidence/llm-reuse.json`: `completed=0`, `reused=20`, токены 0/0. Отдельный сбой — `evidence/llm-unavailable.json`: одна имитация неудачного обращения, остальные не отправлены, факты не изменились.

Этот расчёт покрывает пояснения находок. Живой вызов для описания PR, фактический счёт провайдера, сетевые накладные расходы и расходы интеграции Bult не измерены. Ограничения `LLM_*` ограничивают объём работы, но отдельного предохранителя по сумме денег в прототипе нет.

## Отдельная живая проверка старого помощника на Bult

13 октября существующая Qwen дала свежий ответ через старый путь AI_ENABLED. В контрольном окне журнала две задачи обработали 2562 входных и сгенерировали 203 выходных токена; суммарное время вычислений 47,74905 с. Это реальные счётчики llama.cpp, а не API billing usage и не измерение новой функции 1. Панель модели показывает существующий ресурс L, 1 vCPU / 2 GB, $24/месяц; фактическое списание за запрос не измерено. Формулу per-token нельзя автоматически применять к этому вычислительному тарифу. Подробности, границы измерения и ошибка рекомендации — в [07](07-bult-live-verification.md).
